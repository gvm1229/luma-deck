- Prefer image-centric slides. Keep text-only slides rare and use them only when they satisfy a beta requirement more clearly than a visual slide.
- Never erase, replace, flatten, or reinterpret established deck design elements when refactoring content. In particular, preserve the first-slide background image, the last-slide background image, and the decorative background image applied across the interior slides.
- Screenshot placeholders apply only to foreground content images placed on top of the established slide backgrounds. A missing gameplay screenshot is not permission to remove or replace any background artwork, overlay, texture, or other inherited visual-system asset.
- The first slide is a cover page: use its established full-slide background image only. Do not add a foreground screenshot, screenshot placeholder, image frame, or secondary hero image to the cover.
- Keep the cover metadata tags on one horizontal line at the standard 16:9 presentation viewport. Do not constrain the cover-copy container to make room for a secondary image.
- For the beta deck, use actual in-game screenshots from the current beta build as the primary visual evidence. Do not use init-presentation asset imports, original-game reference shots, editor-only captures, or design graphs as substitutes for current gameplay evidence.
- When a suitable current-build screenshot is unavailable, keep a clearly labeled screenshot placeholder with an exact capture brief. The user will provide or capture the final image later.
- Before putting a numeric gameplay value on a slide, trace the effective runtime value across C++ defaults and current Blueprint class defaults. Project docs can lag behind Blueprint tuning and must not be the sole evidence for balance numbers.
- For technical implementation claims, trace the live C++ call path first and use project docs only as supporting context. Explicitly distinguish C++ defaults, current Blueprint CDO overrides, and runtime behavior.
- Describe the current UI architecture as mixed MVVM, not full-project MVVM. The Hugh and Diana root HUDs create separate local ViewModel instances over shared replicated gameplay sources; some POI, crosshair, enemy HP, and upgrade paths still use direct widget or delegate updates.

Present its verified FieldNotify outputs as HP, recovery, OverDrive, cleanse cooldown, player stats, and related display values. Hacking-puzzle trigger fields belong to separate puzzle ViewModels and should not be generalized to the role HUD.
- Describe GripGun as one server-side camera-viewpoint Line Trace. Do not claim a muzzle-origin trace or a second corrective trace unless the implementation changes.
- Describe RoomCode as a LAN session search key, not authentication, security, or internet matchmaking.
- Explain that the Unreal Engine 5.8 upgrade also expanded the Editor API surface used by the project-owned `UnreelMCP` server; do not frame the upgrade as gameplay-only.

- Do not present AI automation as cost-free or fully autonomous. Pair it with the technical-debt response: Code Intent cards preserve the developer's reason, allowed/forbidden usage, call relationships, authority conditions, Blueprint links, evidence, inferred intent, uncertainty, validation, and future-change warnings.

Preserve the translucent blur, give arrow-owning sibling cards reverse paint order with `:nth-last-child()` z-index values, and keep each arrow pseudo-element at the shared high z-index. Visually verify that the complete circular arrow, including the side overlapping the next card, remains visible.
